# QUALITY — release readiness and measurement
## Automated contract
Stable required job: Kawing release readiness. Run on every branch push, PR, merge_group and manual dispatch. Fail closed on missing governance, configuration, scripts, dependencies or evidence. Use exact Node version from .node-version and one locked package manager. See quality/README for the required script names and report formats. No dummy success scripts, blanket skips or continue-on-error; if a category truly does not apply, accept a meaningful replacement or explicit gate amendment. Reuse test tools and isolated fixtures; library build/catalog and consumer stories replace fictitious app routes.
Reports: native results in unique KAWING_EVIDENCE_DIR, nonempty JSON and actual test/assertion outcomes. Runner checks existence/parse/exit status, not semantic truth. Reviewers inspect coverage and results. Upload sanitized fixture-only evidence; no secrets/customer data. Dependency audit fails on unresolved high/critical findings; exceptions require narrowly governed policy. Check exact dependency/asset licenses and notices. Never change tests to hide failures.
Browser tests: Chromium, reviewed stable screenshots and realistic fixtures; no auto-accept. Test actual authorization/tenant denial and integrity where applicable. Material UI: approved Figma baseline or explicit exception, actual desktop/tablet/mobile rendering; library: Storybook build, variants/states, accessibility, visual regression and affected consumer qualification. Manual review includes full diff, visual approval, migration/backup/rollback and exact release authorization. CI cannot establish WCAG compliance, human review, recovery or production health by itself. Local preview evidence follows AGENTS; CI fixture server is not the owner's preview.

## Research-informed frontend acceptance
For material frontend work, derive observable acceptance criteria from applicable RESEARCH §7 in the existing spec, not a new checklist file. Verify identity/hierarchy, token consistency, truthful content, real navigation/actions, responsive/zoom behavior, relevant interaction and recovery states, required reload persistence, manual keyboard/focus/contrast/target/reduced-motion and representative screen-reader checks. Test trust boundaries, session/cache behavior and unauthorized access where relevant. Measure representative baseline, critical assets/fonts, bundle cost and applicable metrics; prioritize critical rendering before advanced optimizations, avoid lazy-loading likely LCP media. Use existing E2E, accessibility, visual, security and performance scripts; add scoped regressions for objective failures, record pass/fail/not applicable/not run with evidence. Independent human review judges art direction and factual claims; no hardcoded font/color/layout bans or claimed proof of AI authorship. Functional, accessibility, security and integrity failures require repair or approved severity-appropriate exceptions before release. No new tool or service merely to cover the research inventory.
## Documentation and local automation
For material code/config/policy changes, require CHANGELOG and CURRENT plus root README, nearest existing module README and impacted specialist docs. Use approved layout mappings: UI -> DESIGN; server/contracts/migrations or infrastructure config -> ARCHITECTURE; CI/quality -> QUALITY. Core governance, stack manifests and release configuration -> TECHNICAL-OVERVIEW. Review other technical docs semantically. If a required document's facts remain accurate, record a newly added line in CURRENT: "- Reviewed unchanged: path — specific reason tied to this change." This substitutes only for an unchanged document, never CURRENT or CHANGELOG. No timestamp/filler or inherited review note. A material documentation-only change requires CURRENT and CHANGELOG. Pure checkpoint/changelog/evidence maintenance need not create cascading updates. A machine cannot prove semantic freshness; independent review verifies the full diff. Local worktree, staged and pre-push checks inspect candidate content; incomplete governance fails, while a complete blocked checkpoint can be committed/pushed for handoff but cannot pass implementation/release readiness; hosted checks use event commit range. Hooks require installation, no automatic commits/pushes. Protected CI is the enforcement boundary.

## Performance and delivery metrics
Per-commit report: check result/duration, SHA and actual reports. Critical journeys 100% pass; zero unresolved relevant axe violations, critical vulnerabilities or unapproved visual regression. WCAG 2.2 AA includes manual checks. Lab: Lighthouse CI three representative runs, LCP <=2500 ms, CLS <=0.1, TBT <=200 ms (lab proxy, not INP); authenticated fixtures for private routes. Field p75 LCP <=2.5s, INP <=200ms, CLS <=0.1 via Cloudflare Web Analytics or consent-appropriate instrumentation. No data = unknown; set product-specific bundle/latency budgets from evidence.
Ledger quality/delivery-events.json: one verified production rollout per ID, exact SHA, earliest included committedAt (lead-time proxy), deployedAt, failed boolean, recoveredAt if restored, rework boolean for unplanned remediation, evidence URL. CI pass is not a rollout; reconcile Cloudflare and incident evidence, no fabricated failure or recovery. completeFrom/completeThrough only for reconciled interval. Weekly report covers 30 days ending at last reconciled timestamp, reports age and unknown for incomplete coverage. Metrics: deployments/week, median deployment-level lead-time proxy, median recovered failure hours, failure rate, rework rate. No individual ranking. Live ingestion remains separate qualification; no secrets in ledger.

## Enforcement and release
Configure main ruleset: PR, at least one independent approval, code owners, dismiss stale approvals, latest changes approved, resolve conversations, required readiness check, up-to-date branch/merge queue, prevent force push/delete and bypass where supported. Verify actual reviewer access, plan entitlement, rule and deliberate failing candidate; if unavailable, block production release pending explicit owner-approved alternative that verifies equivalent release safeguards. No claim of technical enforcement from procedure alone.
One deployment trigger, exact main SHA and artifact identity: approved Workers Builds synchronous gate or approved GitHub-controlled cutover (disable competing trigger). Require successful checks and release authorization, production version/health/smoke results and rollback. Preserve last known working version. Pin action SHAs; qualify missing config, failed test, absent evidence and passing candidate before enabling. Template does not deploy; see ARCHITECTURE for data/rollback invariants.
