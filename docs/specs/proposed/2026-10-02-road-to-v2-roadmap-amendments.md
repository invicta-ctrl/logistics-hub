# Road to V2 — proposed amendments after V1.1

STATUS: PARTLY DECIDED 2026-10-02. Items 4–7 are accepted, and branch protection (part of item 1) is declined; see `docs/specs/accepted/road-to-v2/2026-10-02-roadmap-amendments.md`. The rest is still a proposal.
AUTHOR: Claude Cloud, on the `road-to-v2/v1.1-experience-foundation` branch, 2026-10-02
INPUTS: all fifteen accepted specs (V1.1 here; V1.2–V1.15 read from their parked branches without changing them), the repository state, and what building V1.1 showed.

The roadmap is sound in what it builds. These proposals are about **how it gets built**: fewer stalls, earlier value, less rework, and gates that catch regressions automatically. Each one is independent and can be accepted or rejected on its own. They are ordered by expected payoff.

## A. Workflow changes, ready now (built in V1.1)

1. **Make CI part of the finish gate** (`.github/workflows/ci.yml`, added in V1.1). It runs build/typecheck, unit tests, the privacy scan, the browser suite and the Worker end-to-end suite on every push to `main`, `road-to-v2/**` and `slice/**`. Workers Builds deploys every push to `main` with no check at all today. *Ask:* turn on GitHub branch protection for `main` so the CI checks must pass (a repository setting only Earl can change), and add "CI green on the final commit" to every slice's finish protocol.
2. **One evidence command for every slice.** V1.1 added `npm run evidence -- --out docs/visual-research/<v> --base main`. It builds both versions, serves each from a throwaway Worker and D1 with fictional accounts, and saves the same screenshot set and median timings. Every later spec demands before/after screenshots at three sizes. *Ask:* add to each slice's visual gate that it "starts from `npm run evidence` and extends `--pages` for its new surfaces". This makes evidence comparable from slice to slice instead of hand-made each time.
3. **Performance budgets from V1.1, not V1.14.** V1.14 sets budgets only at the end. By then thirteen slices could each add a small regression nobody measured. V1.1 recorded a baseline: cold load to first item row about 250 ms locally; section switch about 65–80 ms locally and 208 ms on a slow network; main CSS 12.6 KB gzip; staff chunk 22 KB gzip. *Ask:* each slice's release record compares its `timings.json` with the previous release. Any slice that is more than 20% slower, or whose shared JS/CSS grows by more than 10% gzip, writes a one-line justification or fixes it. V1.14 then audits instead of discovering.

## B. Branch mechanics: a guaranteed conflict and how to avoid it

4. **Every parked branch adds its own `CLAUDE.md`.** On `main` the file doesn't exist; each of the fifteen branches creates a different version of it. When V1.1 merges, every later branch hits an *add/add conflict* on `CLAUDE.md` during its start-gate rebase. *Ask, either:*
   - (a) accept the rule "on a `CLAUDE.md` conflict, keep the version from `main`". The runner text is version-agnostic; the branch's spec, found by its `BRANCH` line, carries everything version-specific. Or
   - (b) Earl puts one shared `CLAUDE.md` and all fourteen remaining accepted specs on `main` now, before V1.2 starts. Identical files then rebase cleanly, and every agent can see the whole roadmap from `main`. That helps slices check what later ones expect, for example the attention contract below.
5. **Two kinds of "complete".** Many slices end in an owner-only production step: applying a D1 migration (`docs/DEPLOYMENT.md` requires it *before* the merge, because `main` deploys automatically), or importing private data (V1.9's official IDs live only on Earl's PC, which the cloud can't reach). With one `STATUS` line, the strict chain stalls at each of these. *Ask:* release records carry `STATUS: COMPLETE` (code, tests and evidence green) and a separate `OWNER_ACTIONS:` list (migration to apply, import to run, with the exact commands, backup and rollback). Prepare a migration slice's owner action as a ready-to-run card, so Earl can do it in one sitting and merge right after.

## C. Sequencing: earlier value, less risk

6. **Swap the order of V1.4 and V1.5's halves.** V1.4 builds an offline staff lease and Catalog PWA *before* any cataloguing workflow exists; its own spec calls it a "foundation". The offline staff lease is the riskiest security work in the roadmap (V1.4 §4), and it would ship with no workflow using it. *Ask:* V1.4 becomes **Rapid Catalogue, online-first** (sessions, sticky location, per-item type, duplicate warning, Review later, bulk metadata). That is immediately useful on office Wi-Fi. V1.5 becomes **Catalog PWA + offline lease**, applied to a workflow that already exists and is proven. Same total scope, value about one slice earlier, and the lease is designed against real use rather than guessed use.
7. **Move V1.9 Staff Directory earlier, right after V1.2.** It needs only the V1.2 media pipeline and the existing accounts and activity; nothing in V1.3–V1.8 feeds it, except that V1.8's identity could *use* it. Its real import is an owner-local step (see 5). Starting it early takes the one owner-blocked slice off the critical path. V1.11 (search) and V1.13 (Staff section) then build on a directory that is already settled.
8. **Shift offline hardening left.** V1.14 is the first slice that systematically tests interruptions (reload, service-worker update, quota, lease expiry, reconnect during sync). *Ask:* each offline-capable slice (the Catalog PWA, Rapid Catalogue offline, Physical Inventory, Self-Service 2.0) ships its own interruption matrix, reusing the V1.0 offline test patterns in `tests/worker-browser/offline-self-service.spec.ts`. V1.14 then becomes the cross-product regression pass the spec intends, not where problems are first found.

## D. Design decisions to settle once, early

9. **Media separation, decided in V1.2.** Four media kinds are coming: catalog photos (V1.2), location photos (V1.3), transaction evidence (exists now, private), and official staff ID scans (V1.9). *Ask:* V1.2 records the rule. Catalog and location images get their own key prefixes and serving path, cacheable only where catalog visibility allows. Evidence stays where it is. **Official ID scans go in a separate private R2 bucket with its own binding**, so a bug in a catalog or evidence route cannot reach them by construction. Each kind gets one retention line in `docs/DEPLOYMENT.md`.
10. **An attention shape before the Attention slice.** V1.3 (can't-find reports), V1.6 (discrepancies), V1.7 (kit shortages) and V1.8 (review records) each create "needs a person" states before V1.10 unifies them. If each invents its own shape, V1.10 starts with a migration. *Ask:* from V1.3 on, each domain exposes its attention-worthy state through one derived query with a common shape (`reason`, record reference, `since`, link). The Stock and Self-Service "Needs attention" views that already exist are the first consumers. V1.10 then aggregates; it doesn't refactor.
11. **Keep the shell at six sections and five phone slots.** V1.12's Operations Home should be the landing page behind the brand link and the post-sign-in redirect, not a seventh section. V1.11's global search should open from a top-bar search button on phones and `Ctrl/Cmd+K` on desktop. The existing `/` shortcut keeps focusing the page's own search. Kits (V1.7) and Locations (V1.3) belong inside Items and Administration → Catalog, not in new top-level sections. This keeps the V1.1 navigation stable through V2, and V1.15 has no navigation rework to do.

## E. Test and evidence hygiene

12. **Independent end-to-end tests.** Several Worker e2e tests depend on records an earlier test created. Running a subset with `-g` fails for that reason, not because of a real defect (seen during V1.1). *Ask:* new tests seed their own records. Existing order dependencies get fixed as each slice touches those tests.
13. **Keep committed evidence small.** V1.1's 20 curated WebP images take 1.1 MB. *Ask:* each slice commits at most about 25 curated images, JPEG or WebP, under about 150 KB each, showing fictional accounts only. The full `npm run evidence` output stays local.

## What V1.1 already did for the roadmap

The shared tokens (`--target`, `--radius-pill`, `--shadow-lg`, the motion durations), the menu and sheet patterns, the CSS-only motion rules and the `npm run evidence` command are in place for V1.2 onward. So are the code preloading on link hover or focus and the slow-network measurement method. Each of these has a consumer in V1.1 itself; none is a placeholder for later slices.
