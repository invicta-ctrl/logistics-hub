## Objective
Turn the existing four-role Ambient Assist and deterministic Intelligent Core into one calm user experience across already shipped V2 surfaces. Staff should never need to initiate an AI conversation or know a model is running to complete work. Background AI may enrich the experience, but every authoritative action and deterministic feature works with AI disabled, stalled, exhausted, malformed, rate-limited, or absent. Preserve human review and verified-correction learning. Add a genuine deployed product-version label and concise version-specific changelog summary inside the **existing Administration > System > This version** section, separately from build fingerprint, commit, built date and migration state.

## Non-negotiable product and release contract
1. **No incomplete product is presented as a complete release.** Never label an unverified build VERSION COMPLETE, RELEASED, DEPLOYED or production-accepted. A coherent, independently functional slice may be merged into main after its own accepted criteria and all applicable checks are green; an unfinished capability or future-version dependency never merges.
2. **Checkpoint discipline.** Every coherent working checkpoint is reviewed, tested as appropriate, committed and pushed to the single active slice branch. Unfinished work is preserved there with a precise handoff. Never hide unpushed checkpoints, leave unrecorded changes, or claim incomplete work finished. Never automatically merge an incomplete checkpoint into main.
3. **Merge discipline.** As soon as a slice is independently useful, complete, non-regressing and green (including verified CI), integrate it into updated main, verify main and its configured deployment, prune only the confirmed-merged slice, then create the next slice from fresh main. The final V1.16 release label is shown only when its complete functionality is approved and actually deployed. A finished slice can land on main without pretending all of V1.16 is finished.
4. **Safe stop.** Missing acceptance authority, ownership conflict, writer lock, check, migration evidence, destructive rollback or provider readiness blocks that affected operation. Report the exact missing gate instead of presenting a partially functional product.
5. **No force/reset/destructive Git.** Preserve unknown work, provenance, historic audit and ledger state. User's reported lifted writer lock is not a substitute for verifying and claiming the prescribed repository lock before a local editor writes.
6. **Cloudflare free-only.** No paid model, upgraded account, additional billed API, or billing change without a new explicit owner amendment. Never consume Neurons merely to use the daily allowance.

## Scope — complete vertical outcomes
### A. Invisible, independent assistance
- No chatbot, floating AI button, explicit AI question field, AI loading gate, AI-generated fake confidence percentage, or visible provider/model in ordinary staff workflows.
- Reuse current Catalogue/Add items photo enrichment where a person already requested/added the photo; capture/save and authorization never wait on inference. Explicit staff choice still governs unverified item identity and policy.
- Candidate enrichment should be triggered by a meaningful authorized domain event, not every page render, search keystroke or stock transaction. Drop stale results and deduplicate by source identity, revision, allowed task and policy version.
- Normal transaction completes first. Deferred/background tasks run only through a bounded reliable mechanism already supported by the repository. Evaluate ordinary Worker execution/background lifecycle before requesting a new Queue; add no new infrastructure without measured justification.
- Optional AI must not share a blocking promise, lock, retry loop or quota-sensitive transaction with core functions. Disable/fail open to normal functionality; deny AI output on privacy/permission validation failure.
- Distinguish graceful visual absence of optional explanations from the preserved deterministic underlying feature.

### B. Intelligent Core remains authoritative
- Consolidate current deterministic catalogue matching/aliases, source-of-truth quantities and movements, search, existing Home/Attention insights and existing count/reconciliation rules. Avoid building replacements or duplicate truth.
- Reuse or precompute approved synonym/alias improvements; normal search works even if all model roles fail.
- Where available data justifies them, add only small **non-predictive, evidence-grounded** contextual hints to existing Home/Attention, Stock/Checks and catalogue surfaces. No new dashboard, duplicate alert list, or invented risk.
- Every hint has current source record(s), state/revision, authorization boundary and stable fallback; never expose restricted borrower, student, staff identity, portrait or proof data to models.
- If the data is insufficient, omit the hint instead of inventing an answer. Approval, quantity adjustment, status transitions and movement postings remain ordinary authorized endpoints.

### C. Verified learning, never unreviewed self-training
- Reuse existing audited Keep/Reject/Correct and catalogue-reviewed evidence. Keep explicitly recorded human correction separate from unreviewed suggestion, guessed match, capitalization-only change, or stale revision.
- Retain learning as bounded and permission-safe evaluation evidence (aggregated outcomes and finite verified examples, not unbounded personal history or raw media). Measure acceptance, correction, abstention, latency and provider cost by role/task without private payload logs.
- Candidate canonical names, aliases, classification knowledge and relationships are versioned proposals with support counts, disagreements, current-record revalidation and authorized review.
- An administrator's approval of a knowledge proposal is NOT an immediate live self-modifying model, policy or prompt. Merge reviewed changes through normal tests, governance, repository version bump and reversible deployment; no autonomous model fine-tuning.
- Keep an explicit policy for correcting a recommendation that turns out wrong; verified staff entry always wins.

### D. Adaptive four-model router and provider evaluation
- Retain narrow roles: Gemma vision; Granite short normalization; Qwen candidate arbitration; GLM rare conflict clarification. No routine model fan-out.
- Verify current provider support/free eligibility/model contract and benchmark at least one permitted challenger for a failing task using bounded, non-sensitive fixtures. Do not silently replace a model based on novelty; require evidence, cost/latency and owner acceptance before role mapping changes.
- Use deterministic-first routing, exact-value allowlists, parser/schema validation, timeout, per-task reservation, single-flight/deduplication, circuit breaker and failure isolation. A result is advisory; model does not write SQL, access unrestricted tables or originate operational intent.
- Original V1.15 daily allowance bands (~8,000 normal; 9,500 app stop) remain provisional until verified account/task consumption and full-app degradation measurements justify amendment. Exhaustion must be a boring no-op for optional enrichment.

### E. Existing Administration > System product version + changelog
- Introduce a single governed product-release metadata source in the existing build pipeline (not a hardcoded UI assertion or public API). It must describe the **actually running artifact**; preserve the existing 12-character build fingerprint, full commit (if available), built-at and migrations.
- Extend the same private authorized System endpoint and the existing **This version** panel. Display a prominent Product version value and a concise, plain-language **What's new** summary for the deployed version. Avoid an additional Admin tab, a new changelog page, or exposing /build.json publicly.
- V1.16 release metadata must enumerate only verified shipped changes: e.g. background assistance isolation, verified learning, improved existing-surface hints and version display, but only where each is truly implemented and accepted. Do not show future features as shipped.
- On malformed/missing metadata show **Unknown**; never infer version from branch, calendar time, commit prefixes or the latest roadmap title. Rollback displays the previous artifact's version and summary. Pre-release/main checkpoint builds must identify their real deployed version; use release manifest/tag mapping subject to current governance. If version metadata's identity is unverified, don't falsely display V1.16.
- Phones/tablets/desktop, keyboard/accessibility, admin-vs-staff access denial, stale app shells, no-public-metadata and fallback are required tests. Version-changelog summary is read-only; no arbitrary Markdown/HTML from user fields.
