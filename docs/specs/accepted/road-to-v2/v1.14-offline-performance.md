## Objective
Stress and harden the entire Road-to-V2 product under poor connectivity, large catalogs/media, concurrent use, Cloudflare Free-plan resource constraints and real mobile conditions while preserving the polished visual experience and speed of normal workflows.

The goal is not maximum cleverness. V1.14 must make the system measurably fast, bounded, recoverable and predictable while removing unnecessary work and avoiding new infrastructure unless simpler measured remedies are insufficient.

## Start gate
Fetch latest main, verify V1.13 completion and safely rebase/bring the V1.14 branch forward according to the Road-to-V2 branch workflow. Capture current production-like performance, Cloudflare usage, offline and recovery baselines before changing behavior.

Do not begin runtime implementation while any predecessor release through V1.13 is incomplete. Planning, fixtures, research and accepted-spec amendments may be prepared in advance.

## Scope
1. Exercise all offline-capable flows under deliberate network loss/reconnect: Self-Service, Catalog PWA, Rapid Catalogue and physical-inventory sessions.
2. Test interruption cases including reload/app restart, service-worker update, queued photos, low storage/quota pressure, authorization lease expiry and reconnect during sync.
3. Test concurrent/multi-device state changes and human-readable conflict handling. Never silently overwrite newer authoritative state or discard local evidence.
4. Review queue idempotency/retry behavior so reconnects or repeated sync requests do not duplicate transactions.
5. Establish deterministic scale fixtures for current-like, growth and stress tiers. At minimum cover catalog/media, inventory movements/activity history, Staff Directory, loans/open units, Self-Service records and attention/search workloads. Use approximately current scale, ~10x growth and ~100x isolated stress where practical rather than relying only on a 500-item fixture.
6. Establish measured performance budgets from the V1.13 baseline for startup, route transitions, common API calls, search, large lists, image-heavy surfaces, browser main-thread work, DOM growth, response sizes and memory trend. Fix regressions and record justified exceptions rather than relying on subjective “feels fast”.
7. Enforce bounded-work behavior on growing surfaces: potentially large APIs must not return unlimited collections without justification; large UI lists must not create live DOM proportional to total record count; histories must be bounded; media loading must be demand-driven.
8. Audit all hot D1 paths using representative SQL, `EXPLAIN QUERY PLAN` and available D1 metadata such as duration, rows read/written/returned. Add, change or remove indexes only when evidence shows a material benefit. Preserve movement-derived inventory authority.
9. Audit Worker request count, Worker CPU, D1 rows read/written/storage, R2 storage/Class A/Class B operations and request/subrequest amplification. Model realistic daily/monthly Hub usage against the current Cloudflare Free-plan limits and preserve generous operating headroom.
10. Audit asset delivery: image variants, lazy loading, cache policy, service-worker cache size/eviction, font/CSS/JS weight and layout shift. Avoid unnecessary R2 list/read operations and prevent media failures from blocking core operational workflows.
11. Audit refresh behavior and remove unnecessary polling/re-fetching. Prefer revision/version checks, browser/CDN caching, bounded retries and explicit refresh where correctness allows.
12. Audit animations and view transitions for jank on representative mobile conditions. Motion must degrade gracefully and never hold application state changes hostage.
13. Harden install/update flows on Android/Chromium and iPhone/iPad guidance. Preserve unsynced data through update where architecturally possible and provide clear recovery guidance otherwise.
14. Perform a cross-product accessibility stress pass: keyboard, focus restoration, large text, reduced motion, color/contrast, screen-reader names, touch targets and orientation/responsive changes.
15. Review security/privacy implications of offline caches, private R2 URLs, Staff Directory media, remembered Self-Service identity and authorization leases.
16. Exercise failure isolation: optional media, dashboard metrics, telemetry and enhancement failures must not unnecessarily block stock, loan, return or other critical paths.
17. Rehearse recovery procedures for representative D1/R2 incidents, including D1 Time Travel/restore documentation, exact-target verification, post-restore integrity checks and detection of orphan/stale media metadata relationships.
18. Produce a lightweight recurring resource/performance evidence path using existing provider telemetry and repository test tooling before considering any custom observability subsystem.

## Cloudflare resource envelope
V1.14 must verify the current provider limits from official Cloudflare documentation at execution time; hard-coded limits in planning material are snapshots, not permanent assumptions.

Normal product operation should target a low fraction of the available Free-plan envelope. Use the doctrine's default operating bands unless evidence justifies an accepted amendment:

- expected/green: at or below roughly 20% of a shared provider allowance;
- caution/investigation: above roughly 35%;
- protective action: at or above roughly 50% before additional load-producing rollout.

Separate normal user traffic from migrations, recovery drills, bulk imports, load tests and development traffic. The objective is not to prove that abuse can never exhaust a quota; it is to ensure the product is never intentionally designed to operate close to a free-tier ceiling.

## Database hardening rules
- D1 remains structured operational truth; R2 remains governed file/media/evidence storage.
- Inventory quantity remains movement-derived from the append-only ledger.
- No mutable `current_quantity` or similar second authority may be introduced for performance convenience.
- No materialized balance/read model may be introduced until query plans, indexing and bounded caller scope have been measured and proven insufficient.
- Any cache or summary layer added in V1.14 must be reconstructable and explicitly non-authoritative.
- Schema/index changes use new additive migrations only; never rewrite or replay previously applied migrations.
- Avoid full-ledger/full-table work on routine requests where a selective bounded path is practical.

## Complexity gate
For every proposed new performance/reliability mechanism, record:

1. the measured problem;
2. the failure/resource consequence of leaving it unchanged;
3. the simpler alternatives attempted or rejected;
4. the new operational/failure modes introduced;
5. measurement and rollback/recovery evidence.

Do not add Redis, Elasticsearch, a second operational database, an event bus, generic repository framework, permanent distributed cache or other infrastructure merely as future-proofing.

## Performance and scale evidence
The final evidence must make layer attribution possible. For representative hot paths capture, where available:

- end-to-end action/request latency;
- Worker CPU time;
- D1 SQL duration and rows read/written/returned;
- query plan for known hot SQL;
- request and subrequest count;
- API response size;
- R2 operation/object-size behavior;
- browser main-thread time and style/layout work;
- live DOM count/growth behavior for large lists;
- memory trend over repeated navigation/use;
- offline queue/cache/storage growth.

A large-list acceptance test must demonstrate that increasing total records does not produce equivalent linear growth in live rendered DOM during ordinary browsing.

## Acceptance criteria
- Offline-capable workflows survive tested interruptions without silent data loss.
- Sync/retry is idempotent for covered transaction classes.
- Conflicts preserve both evidence and current authoritative state and present understandable next steps.
- Current-like, ~10x growth and practical stress fixtures expose no unexplained unbounded routine work on covered hot paths.
- Large list rendering remains bounded rather than scaling live DOM linearly with total collection size.
- Growing APIs/histories/media paths are bounded or have an explicit measured justification for remaining unbounded.
- Hot D1 queries have recorded query-plan/rows-read evidence, with no avoidable routine whole-table/whole-ledger scans at tested scale.
- Images, caches, queues and service-worker storage are bounded and do not grow without control.
- Cloudflare Worker/D1/R2 consumption is modeled against current Free-plan limits and normal expected operation remains inside the doctrine's healthy resource envelope, with documented exceptions if any.
- Optional-media/metrics/telemetry failures do not unnecessarily block critical operational workflows.
- Common animations remain smooth enough under representative conditions and reduced-motion paths work.
- Android/iOS install/update guidance is revalidated.
- Privacy/security review finds no unintended private-media/public-cache exposure.
- Recovery rehearsal documents exact target, restore/recovery procedure, integrity verification and known limitations.
- Full relevant unit/integration/browser/offline tests, build, privacy/secret scan, accessibility, performance evidence and final diff review pass.

## Exclusions
