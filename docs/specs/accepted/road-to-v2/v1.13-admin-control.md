## Objective
Turn Administration into a clear operational control room for authorized administrators/owners, consolidating settings and system visibility without exposing developer-only complexity to ordinary staff.

## Start gate
Fetch latest main, verify V1.12 completion and safely rebase.

## Information architecture
Organize Administration into coherent sections rather than one long mixed page:
- **Self-Service** — open/closed state, identity/evidence rules and supported transaction behavior.
- **Catalog** — categories, locations, kits, catalog visibility/completeness policies where appropriate.
- **Staff** — Staff Directory, accounts, roles and sessions.
- **Accountability** — evidence retention/review behavior and related privacy controls.
- **System** — version, deployment/build identity, D1/R2 connectivity, migration level, backup/restore status and relevant operational health.

## Scope
1. Rework Administration navigation/layout around the sections above while preserving existing permissions and settings.
2. Present system state in human language. An owner should be able to tell whether the application, D1, R2 and Self-Service are operational without opening Cloudflare for routine checks.
3. Surface production version/build/commit identity and current migration level from trustworthy data; do not fabricate provider health.
4. Surface last known backup/restore evidence from the existing control-center/runbook architecture where it can be verified safely. Do not expose credentials or private backup contents.
5. Integrate Staff Directory/account management without duplicating its domain logic.
6. Improve role/permission management presentation and make consequential changes show clear impact before submission.
7. Centralize settings descriptions so administrators understand what each switch changes. Avoid duplicate configuration truth across UI, environment variables and database settings.
8. Add health checks that are bounded and cheap. A transient optional health probe failure must not break normal Administration rendering.
9. Preserve the current production boundary: D1 migrations, restore, deployment and destructive maintenance require exact targets, preflight, backup/rollback and verified post-change evidence.

## Visual research and rendered review
Create `docs/visual-research/v1.13.md`. Research modern settings/control-center information architecture, system-status presentation, role management and destructive-action UX. Use current official design systems and real admin products.

Capture and visually inspect each Administration section, mobile/tablet/desktop navigation, healthy/degraded health states, role/settings forms, confirmation states and empty/unavailable evidence states. The agent must inspect screenshots rather than accepting layout from code alone.

## Acceptance criteria
- Administration is logically organized and role-gated.
- Existing settings continue to work and have one authoritative storage/config source.
- System/version/migration/backup information is truthful and traceable to verified state.
- No credentials/private backup contents leak to UI or logs.
- Consequential admin changes have clear confirmation/impact text and audit behavior.
- Health checks are bounded and cannot materially slow ordinary staff workflows.
- Required tests, build, privacy/security scan, browser/E2E, accessibility, performance evidence, visual evidence and final diff review pass.
