# Road to V2 — V1.1 Experience Foundation & Navigation

STATUS: ACCEPTED BY OWNER FOR IMPLEMENTATION
ROADMAP: Road to V2
VERSION: V1.1
BRANCH: `road-to-v2/v1.1-experience-foundation`
BASELINE: V1.0 production/main after the V1 release-close work is complete
PREDECESSOR: V1.0 closure on `main`

## Objective
Establish the durable information architecture, interaction language, motion foundation, and responsive staff shell that every later Road-to-V2 slice can build on. V1.1 must be a complete deployable improvement by itself; no placeholder modules or dead navigation may ship.

## Start gate
Before implementation, fetch `origin/main` and verify that V1 is explicitly closed on main, all Part 1–6/V1 close work is green, and no unresolved release-close writer owns the shared worktree. Rebase this branch safely onto latest main. If the V1 baseline is not explicitly complete, stop and report that single blocker; do not implement against a moving V1 target.

## Scope
1. Reorganize the staff information architecture to the human mental model: **Items | Stock | Loans | Self-Service | Activity | Administration**. Move My Account behind the staff identity/avatar instead of keeping it as an operational module.
2. Rename staff-facing “Inventory” surfaces to **Items** where the screen describes what an item is. Preserve **Stock** for physical quantity/stock operations.
3. Design a mobile navigation that remains usable at narrow widths. Primary mobile destinations should be Items, Stock, Loans, Self-Service, plus a More surface for Activity, Administration and Account as role permits.
4. Perform a terminology pass on touched screens. Prefer plain operational language over internal/database terms. Do not rename domain values in storage merely for copy changes.
5. Establish shared visual tokens and interaction primitives using the existing semantic HTML/CSS/TypeScript stack: spacing, typography hierarchy, radii, elevation, status treatments, cards, sheets/dialogs, focus states, touch targets, empty states, loading/skeleton states and responsive breakpoints.
6. Establish a lightweight motion system. Use CSS/Web platform capabilities first. Motion should normally use transform/opacity, be interruptible, never block interaction, and respect `prefers-reduced-motion`.
7. Preserve current V1 functionality, permissions, ledger invariants, offline Self-Service behavior, D1/R2 boundaries and no-framework direction.

## Visual research and evidence — mandatory
A code review is not sufficient to call the design improved.

Before finalizing the visual direction, use browser/web research to inspect current, high-quality references relevant to navigation, admin shells, responsive tables/cards and motion. Prefer official design systems and real product interfaces (for example Apple HIG, Material Design, Shopify Polaris, Atlassian, GOV.UK, modern inventory/admin products). Do not copy a brand; extract interaction principles that fit HAU USC.

Create `docs/visual-research/v1.1.md` containing:
- sources/URLs and access date;
- patterns adopted, rejected, and why;
- baseline screenshots of relevant V1 screens;
- after screenshots at desktop (~1440 px), tablet (~768 px) and phone (~390–430 px);
- visual findings from the agent’s own image/screenshot inspection, not only DOM/code assertions;
- accessibility and performance observations.

The agent must inspect the rendered screenshots visually and iterate if hierarchy, spacing, clipping, contrast, balance or mobile usability is poor.

## Performance and accessibility
- Do not add a heavy UI or animation dependency for this slice.
- No meaningful regression in measured startup/interaction performance versus the captured baseline.
- Maintain keyboard operation, visible focus, semantic landmarks, screen-reader names, adequate touch targets, large-text resilience and reduced-motion behavior.

## Acceptance criteria
- Staff navigation matches the new information architecture and all visible links work for the roles that can access them.
- Account access is intuitive from the identity/avatar area and remains fully functional.
- Desktop, tablet and phone layouts are visually coherent and usable.
- Touched pages use the shared tokens/primitives rather than page-specific ad-hoc styling where practical.
- No existing staff workflow or Self-Service workflow regresses.
- The visual research/evidence document exists and includes actual screenshot review.
- Typecheck, focused tests, full relevant tests, build, browser/accessibility checks, privacy scan and final diff review pass.

## Finish protocol
When the user says `complete` or `finish`, reconcile the entire branch against these acceptance criteria, finish all missing work, run the required gates, review the complete diff, and create `docs/road-to-v2/releases/v1.1.md` with the final commit, migrations (if any), verification evidence, visual evidence locations, known limitations and `STATUS: COMPLETE`. Commit and push coherent green work. Normal integration to `main` is authorized by the user’s `finish` command once all gates are green; production/provider mutations outside the accepted slice still require their normal migration/backup controls. Do not delete or modify the other parked Road-to-V2 branches.

## Exclusions
No item-photo data model, reusable location model, Catalog PWA, kit model, Staff Directory, intelligent search or new analytics in V1.1. Do not create speculative hooks for later releases.
