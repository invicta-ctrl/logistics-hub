Import the existing official-ID archive safely without placing personal ID images or extracted personal data in public Git.

## Verified source structure
The source archive is department-folder based and contains front/back PNG pairs using names similar to `Tanglao_Front_DoL.png` and `Tanglao_Back_DoL.png`. Departments include DoL, DoF, DHR, DEM, DCES, DPC, DBR, SEC, OVP and OfP plus an OFFICERS source folder. The OFFICERS folder is not itself the person’s department: filenames contain the actual department code (for example a DoL officer remains DoL with an officer role/status).

## Import rules
1. Pair ID scans deterministically using normalized source identity + department code + Front/Back, never surname alone.
2. Produce a preflight report before any private upload: complete pairs, missing fronts, missing backs, duplicates, ambiguous matches and unknown codes.
3. Do not commit scans, derived thumbnails, OCR output, private manifests or staff personal data to public Git.
4. Store directory metadata in D1 and official-ID media in a dedicated private R2 bucket with its own Worker binding, never the catalog/location media or transaction-evidence bucket, so a defect in another media route cannot reach staff IDs. Creating that bucket in production is an owner action recorded in the release record. Apply strict access controls and retention/governance appropriate to staff records.
5. Do not add facial recognition or identity matching from faces. Do not depend on OCR for authoritative staff fields. Human-reviewed/private staff records remain authoritative for profile data.
6. Normalize department display names professionally rather than exposing informal source-folder labels.

Data note (Earl, 2026-10-03): the directory is not the 0001 `staff_users` table. `staff_users` holds the authorized DOL staff, filled privately by `scripts/build-private-staff-seed.mjs`. `staff_directory` (migration 0021) is for looking people up and tracking their usage, and grants nothing. V1.3 neither reads nor writes `staff_users` (`docs/DATA_ARCHITECTURE.md`).

## Directory UX
Add `Administration → Staff Directory` with:
- department-grouped browsing and search;
- visual staff cards/profile images derived from approved private media where permitted;
- role/department/status summary;
- staff profile sections: **Profile | USC ID | Usage | Loans | Activity**;
- USC ID viewer with private front/back images and fast, polished transitions/zoom; access must be permission-gated and audited as appropriate;
- Usage views for inventory/pantry/consumable activity using existing immutable transaction data, with date/item/category filters;
- current and historical loans;
- relevant Logistics Hub activity/audit information.

## Account linkage
Allow an authorized administrator to link a directory person to a Logistics Hub staff account through stable internal IDs. Once linked, authenticated staff workflows may use verified staff identity rather than repeatedly asking for typed name/ID where policy permits. Do not infer linkage from surname/photo automatically.

## Permissions/privacy
Define and test a role matrix. Basic directory identity and highly sensitive ID imagery/activity history do not need identical visibility. Follow least privilege. Never expose staff ID scans through public/Self-Service/catalog APIs or caches.

## Acceptance criteria
- Staff Directory is private, permissioned and department-organized.
- Importer pairs front/back files correctly and reports ambiguity before writes.
- OFFICERS records preserve actual department plus officer role/status.
- No production ID scans or private staff data enter Git.
- Authorized users can view profile/ID/usage/loans/activity; unauthorized users cannot.
- Account linkage is explicit, auditable and stable.
- Usage and loan history are derived from existing authoritative records, not copied into a second ledger.
- ID viewer and directory remain responsive and visually polished without leaking private media into public caches.
- Required security/privacy tests, migrations/data verification, build, browser/E2E, accessibility, visual-fixture evidence and final diff review pass.

## Finish protocol
