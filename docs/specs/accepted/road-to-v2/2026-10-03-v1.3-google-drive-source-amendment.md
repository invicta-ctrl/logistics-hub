## Decision

The authorized private source of the staff ID scans is the Google Drive folder **`010. Official IDs`** (its link is in Earl's instruction and is kept out of this public repository), instead of the local Windows path `D:\Documents\HAU-USC Logistics Hub\references\Official IDs`. The actual Drive structure and file names are authoritative over assumptions made from the former path. Everything else in the V1.3 specification stands.

## Requirements carried by this amendment

- Drive is read-only source data: enumerate and download only; never modify, move, share or trash anything there.
- Nothing from the source enters Git: no scans, thumbnails, OCR output, private manifests, extracted personal data or temporary downloads. Committed tests and visual evidence use synthetic images only.
- The V1.3 architecture is unchanged: directory metadata in D1; scans in the dedicated private `STAFF_IDS` bucket; explicit permissions and audit; deterministic Front/Back pairing by normalised identity + department code + side (never surname alone); OFFICERS keep the department their file name encodes, with officer status beside it; a preflight report before any production write.
- No production import until the preflight is clean or unresolved records are excluded for later review. No facial recognition; OCR is never authoritative; account linkage is explicit and auditable.
- If an owner-only production dependency is unavailable (bucket creation, the migration, the owner's sign-in), the slice completes with the real source used for private validation where safe and the exact remaining steps recorded under `OWNER_ACTIONS`; succeeding slices continue under `CLAUDE.md`.
- Temporary downloads are removed after verification, and the final diff is checked for import residue.

## How it was applied (2026-10-03)

The cloud session could read the folder through the Google Drive connector (metadata and listing; read-only). It found `[DEM] Official ID` with two complete Front/Back pairs (four PNG files) and an empty `[DoL] Official ID`; there is no `OFFICERS` folder and no other department folder yet. The preflight ran privately on that listing (clean). Downloading the scan bytes into the cloud session was not done: the connector returns a file as text in the model's context, which would put ID images into a transcript, and the production writes need the owner anyway. The import is therefore an in-app owner step (Administration → Staff Directory → Import ID scans, from the downloaded Drive folder), recorded with its exact procedure in `docs/DEPLOYMENT.md` ("V1.3 Staff Directory") and `docs/road-to-v2/releases/v1.3.md`.

Follow-up the same day: Earl asked for the owner steps to be done "referring to the file names and the image", with the 2026-27 USC Directory of Officers and Executive Staff (a Google Sheet; link in Earl's instruction) as a further reference. The four scans were then viewed through the connector, read-only, only to cross-check that the names printed on them match the sheet. The sheet stays the authority for profile fields, and nothing from the scans or the sheet entered Git. The release record tracks the owner steps.
