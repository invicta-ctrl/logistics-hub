# V1.14 Hardening Plan — Offline, Performance & Reliability

STATUS: PREPARED; RUNTIME EXECUTION BLOCKED BY V1.14 START GATE
SPEC: `docs/specs/accepted/road-to-v2/v1.14-offline-performance.md`
BRANCH: `road-to-v2/v1.14-offline-performance`

This is the execution checklist for V1.14. It does not authorize work before the accepted spec's start gate. Until V1.13 is complete and V1.14 is brought forward safely, only planning/research/fixture preparation that cannot disturb predecessor work is allowed.

## Operating principle

Make routine work bounded, measurable and recoverable. Prefer removing unnecessary work over adding infrastructure. Add complexity only when the measured simpler remedies are insufficient.

- [ ] Confirm writer ownership/lock and clean expected working state.

- [ ] Re-check current Cloudflare Workers, D1 and R2 limits/pricing from official documentation.
- [ ] Record current production-like entity counts, database size, R2 object/storage estimates and current provider usage where safely available.

**Exit evidence:** start-gate note with refs/commit, current provider-limit snapshot and baseline system scale.

## Phase 1 — Measurement layer and baseline

### 1A. Define hot user paths

At minimum benchmark:

- [ ] staff Items/catalog list;
- [ ] item profile/detail and bounded history;
- [ ] Stock/reorder surfaces;
- [ ] Loans/returns/open units;
- [ ] Activity feed/search/attention filters;
- [ ] Self-Service read/sync paths;
- [ ] Staff Directory/search;
- [ ] Catalog PWA startup/search;
- [ ] Rapid Catalogue and physical-inventory sessions where present;
- [ ] media thumbnail/detail loads.

### 1B. Capture layer-specific metrics

For covered paths collect, where available:

- [ ] end-to-end latency;
- [ ] Worker CPU time;
- [ ] D1 duration, rows read/written/returned;
- [ ] query plans for hot SQL;
- [ ] Worker request/subrequest count;
- [ ] response bytes;
- [ ] R2 request count and object bytes;
- [ ] main-thread/style/layout time;
- [ ] live DOM count and growth;
- [ ] memory trend during repeated navigation;
- [ ] cache/offline-queue/storage growth.

Do not create a custom analytics product just to measure these. Use existing provider/browser/test tooling and the smallest repository-native harness that makes regressions reproducible.

**Exit evidence:** baseline report that attributes cost to database, Worker/network, media or browser rather than combining everything into one number.

## Phase 2 — Deterministic scale fixtures

Create/reuse deterministic fixtures for three tiers:

### Tier A — current-like

- [ ] Approximately current production catalog and ledger dimensions.
- [ ] Representative media coverage and Staff Directory data.

### Tier B — growth

- [ ] Roughly 10x important collection/history dimensions.
- [ ] Enough media to expose R2/cache/list behavior.

### Tier C — stress

- [ ] Roughly 100x for isolated read/query/list tests where practical.
- [ ] May use subsystem-specific dimensions rather than creating a needlessly huge full-system fixture.

For each tier:

- [ ] keep generation deterministic/repeatable;
- [ ] avoid real PII/evidence;
- [ ] measure storage/time required to prepare the fixture;
- [ ] keep the fixture/harness itself from becoming a heavy dependency.

**Exit evidence:** reproducible fixture command/data description and baseline results at all practical tiers.

## Phase 3 — Frontend bounded-work audit

### 3A. Large lists

For every growing list/table/grid:

- [ ] determine whether API results are bounded;
- [ ] determine whether client state grows with the entire result set;
- [ ] determine whether live DOM grows linearly with total records;
- [ ] use virtualization/windowing and/or bounded paging only where collection scale justifies it;
- [ ] preserve accessibility, focus, keyboard interactions and scroll behavior;
- [ ] verify sorting/filtering/search semantics remain correct.

**Invariant:** ordinary browsing at 500, 5,000 and larger practical fixtures must not require equivalent linear growth in live rendered DOM.

### 3B. Layout/script weight

- [ ] remove unnecessary wrapper-heavy markup on hot repeated rows/cards;
- [ ] measure expensive style/layout work before optimizing;
- [ ] check route transition/main-thread blocking under representative mobile conditions;
- [ ] audit JS/CSS/font weight for accidental growth;
- [ ] ensure animation/view-transition failure cannot block state changes.

**Exit evidence:** before/after DOM, layout/main-thread, route and responsiveness measurements.

## Phase 4 — D1/database audit

### 4A. Hot-query inventory

For each hot endpoint/query:

- [ ] record SQL/query shape and caller limit;
- [ ] record `EXPLAIN QUERY PLAN`;
- [ ] record representative rows read/written/returned and duration;
- [ ] flag full scans, avoidable correlated work, deep offsets and repeated aggregates;
- [ ] verify growing histories/collections are bounded.

### 4B. Remediation order

Apply fixes in this order unless evidence justifies otherwise:

1. [ ] narrow requested columns/scope;
2. [ ] bound/paginate the caller;
3. [ ] improve predicates/query shape;
4. [ ] add/change the narrowest measured index;
5. [ ] use safe request-level/browser caching for reconstructable reads;
6. [ ] only then consider a materialized/reconciled read model.

### 4C. Inventory balance

- [ ] specifically benchmark movement-derived `inventory_balances` at growth/stress tiers;
- [ ] verify item-scoped and full-list plans separately;
- [ ] test index/query-shape improvements before any materialization proposal;
- [ ] retain movement ledger as the sole authoritative quantity source.

### 4D. Index hygiene

- [ ] identify redundant/unused indexes only with evidence;
- [ ] evaluate write/storage cost of proposed indexes;
- [ ] use additive migrations for any schema/index changes;
- [ ] never edit/replay applied production migrations;
- [ ] run appropriate optimization/verification after index changes.

**Exit evidence:** hot-query matrix with before/after plans and resource measurements.

## Phase 5 — Cloudflare resource-envelope audit

Revalidate official limits first. Then model normal user behavior and realistic high-activity days/months.

### 5A. Workers

- [ ] requests per common action;
- [ ] repeated/background requests;
- [ ] CPU distribution on common routes;
- [ ] subrequest amplification;
- [ ] accidental polling/request storms.

### 5B. D1

- [ ] rows read/day model;
- [ ] rows written/day model;
- [ ] storage growth model;
- [ ] identify endpoints disproportionately consuming rows read;
- [ ] verify no read-only interaction creates unnecessary writes.

### 5C. R2

- [ ] storage growth model;
- [ ] Class A operation model;
- [ ] Class B operation model;
- [ ] unnecessary `list`/metadata/read calls;
- [ ] oversized image/object delivery;
- [ ] cache effectiveness where privacy allows.

### 5D. Operating bands

- [ ] normal expected usage remains in green (target <= roughly 20% of shared allowance);
- [ ] investigate anything modeled above caution (> roughly 35%);
- [ ] require corrective action/accepted exception at protective threshold (>= roughly 50%).

Separate production user activity from imports, migrations, restore drills and load tests.

**Exit evidence:** quota/resource model with assumptions, current usage and identified safety margin.

## Phase 6 — Media, caching and refresh behavior

- [ ] verify list thumbnails vs detail/profile variants;
- [ ] lazy-load non-critical media;
- [ ] reserve image dimensions/layout space;
- [ ] verify cache/versioning policy and privacy boundary;
- [ ] verify service-worker cache is bounded and evicts safely;
- [ ] verify missing media cannot block core operations;
- [ ] eliminate unnecessary R2 listing on user paths;
- [ ] find repeated payload refetches that can use revision/version/cache validation;
- [ ] eliminate high-frequency polling unless correctness genuinely requires it;
- [ ] verify retry backoff prevents storms.

**Exit evidence:** media/cache/request-count comparison and cache/storage ceiling behavior.

## Phase 7 — Offline, concurrency and durability

Build a fault matrix covering at least:

- [ ] offline before action;
- [ ] network loss during action;
- [ ] reconnect after queued action;
- [ ] reload/app restart with unsynced work;
- [ ] service-worker update with unsynced work;
- [ ] authorization/lease expiry while offline;
- [ ] duplicate/repeated sync request;
- [ ] two devices changing related state;
- [ ] conflicting newer authoritative state;
- [ ] queued media upload failure;
- [ ] local storage/quota pressure;
- [ ] partial optional dependency failure.

For every state-changing workflow verify:

- [ ] authoritative commit point;
- [ ] idempotency/duplicate behavior;
- [ ] retry safety;
- [ ] conflict behavior;
- [ ] user-visible recovery state;
- [ ] preserved evidence/auditability.

**Exit evidence:** offline/conflict matrix with pass/fail, reproduction steps and fixes.

## Phase 8 — Failure isolation, recovery, security and accessibility

### 8A. Failure isolation

Verify that failure of each optional subsystem does not unnecessarily block critical operations:

- [ ] item/profile image;
- [ ] dashboard/summary metric;
- [ ] analytics/telemetry;
- [ ] decorative animation/view transition;
- [ ] enhanced search path;
- [ ] non-critical background refresh.

### 8B. Recovery

- [ ] rehearse documented D1 recovery/Time Travel path in a safe target;
- [ ] verify exact target and rollback/recovery controls;
- [ ] run post-recovery integrity checks;
- [ ] check D1↔R2 orphan/stale metadata relationships;
- [ ] record RTO-style human steps and known limitations without inventing unsupported guarantees.

### 8C. Security/privacy/accessibility

- [ ] audit private media/cache exposure;
- [ ] audit remembered identity/offline authorization data;
- [ ] run privacy/secret scans;
- [ ] keyboard/focus restoration;
- [ ] large text/orientation/responsive behavior;
- [ ] reduced motion;
- [ ] screen-reader names;
- [ ] touch targets/color/contrast.

**Exit evidence:** recovery, privacy/security and accessibility reports.

## Phase 9 — Complexity review and final consolidation

For every new cache, background mechanism, summary/read model, replica, queue, index family or library added during hardening:

- [ ] link the measured problem it solves;
- [ ] state why a simpler solution was insufficient;
- [ ] document failure/maintenance cost;
- [ ] prove before/after benefit;
- [ ] document rollback/removal path.

Remove experimental mechanisms that failed to justify themselves.

Potential advanced mechanisms are not default tasks:

- D1 read replication/Sessions: only if measured placement/network latency materially dominates relevant reads.
- Materialized read models: only if measured aggregates remain too expensive after query/index/bounding work.
- Dedicated search infrastructure: only if D1-based search fails measured V2 requirements.
- Background queues/workers: only if request-path execution is demonstrably unsuitable.

## Stop/ask conditions during V1.14

Stop and seek an accepted amendment instead of smuggling scope when hardening appears to require:

- a new major product feature;
- replacement of D1 or R2;
- a second authoritative stock/balance model;
- a new external infrastructure service;
- a broad framework rewrite;
- material privacy/security behavior changes outside the accepted hardening scope.

Measured index/query/list/cache/retry/recovery improvements that preserve existing product behavior remain within V1.14 when supported by the accepted spec.
