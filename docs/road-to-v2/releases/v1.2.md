## What shipped

- **Item photos.** One primary photo per item. Any signed-in staff member (the same people who can edit an item) can add, change or remove it from the item's profile. Add and Change show a preview first and save only on "Save photo"; Remove asks first. Every change is an Activity entry (`ITEM_PHOTO_ADDED`, `_REPLACED`, `_REMOVED`) and a line in the item's History.
- **Storage.** Image objects in a new private R2 bucket (`CATALOG_MEDIA`, `logistics-hub-catalog-media`), apart from loan photos (`EVIDENCE`); structured metadata in D1 (`item_media`, migration `0020`: item, random media id, width, height, who, when). A replacement gets a new id, so a stored image is never overwritten in place. Photos are served only to signed-in staff, never on the public Lending Hub, Self-Service or their catalogs (tested).
- **Processing path.** The browser decodes with the camera's rotation applied and re-draws two JPEGs on a canvas: 1280 px (viewer) and 320 px (lists and profile). The original never leaves the device. The Worker accepts only plain 8-bit JPEGs within 1600/480 px and 1 MB/150 KB, refuses one that still needs rotating, and rebuilds each file without EXIF, location, colour profile, comments or trailing bytes (header lengths are checked too).
- **Consistency.** R2 is written first; one D1 batch switches the reference only if the item still has the photo the client saw; the old files go afterwards. D1 therefore never points at a missing file; a failed or refused write leaves the old photo untouched; an error after the batch may have committed keeps the new files. The only possible residue is an unused file in R2 (a failed delete), which nothing refers to.
- **Profile.** The item sheet opens with the photo beside availability, status tags, type, category and place, then the existing tabs (stock, loan, edit, history all unchanged).
- **Photo interactions.** A thumbnail or the profile photo opens a modal viewer that grows from it with a view transition (a plain fade without the API, instant under reduced motion); Escape, Back and Close return to the profile with focus restored.
- **List.** A fixed 40 px lazy thumbnail (or a quiet placeholder) leads each row. Filtering, sorting, views and keyboard row navigation are unchanged.
- **Fixes found on the way.** A file picker's own cancel event closed the whole sheet (also true of the loan form's photo picker); the router now treats the address a view mirrors into the URL as already rendered; the Items "kicker" no longer repeats the category; tablets keep the item column wide.
- **Tooling and tests.** `npm run evidence` gains `item-profile` and `item-photos` scenes (synthetic pictures drawn in the browser; list weight and layout shift with 300 photos).

## Performance (local Worker and D1, headless Chromium, medians)

The first version of the list was about 25 ms slower than V1.1 on a cold load. Measured properly (25 interleaved runs per tree, Chrome's script, layout and style counters), the cause was 1,198 extra DOM nodes (three wrappers per row over 397 rows), which cost about 13 ms of layout and style. The rows now add no wrapper elements (an item without a photo adds none, one with a photo adds only its image). After the fix the two trees are level: first row 181 vs 184 ms (V1.1), layout 86 vs 87 ms, total task time 300 vs 299 ms, DOM nodes 13,291 vs 13,282. Details in `docs/visual-research/v1.2.md`.

## Known limitations

- **Research provenance.** Sources in `docs/visual-research/v1.2.md` come from search-result summaries, not full page reads. Earl allowed the research, but the allowance did not reach the running session (the pages were still refused when retried), so a re-read needs a new session after the network setting is saved. The hosts are `web.dev`, `developer.chrome.com`, `developer.mozilla.org`, `m3.material.io`, `polaris-react.shopify.com` and `w3.org`.
- **Not tested on real devices.** Phone cameras, HEIC photos, iOS Safari (`<dialog>`, view transitions, picker behaviour) and screen readers were not available. The decode path was exercised with a JPEG that carries an EXIF rotation and GPS text.
- **The scan data cannot be inspected without decoding.** The Worker removes every metadata segment and checks every header, so for browser-made images nothing about the place a photo was taken survives; a hand-made client could still hide bytes inside the compressed scan.
- **Photos are staff-only.** The public Lending Hub and Self-Service show no pictures; showing them is a later decision, not part of this slice.
- **One photo per item**, any signed-in staff member can change it (as with other item edits); no per-role restriction.
- **An unused file can remain in R2** if a delete fails after a replace or remove; nothing in D1 refers to it. There is no sweeper for them.
- **Browser cache.** A removed photo can stay in a staff browser's private cache for up to a day, if someone knows its (random) address.
- **Duplicated availability.** The profile and the Overview's quantity editor both show the on-hand figure; the profile one must stay visible on every tab.
- **Timing** was measured locally only (level with V1.1 after the row fix above); not measured against production.
- **End-to-end test order.** As in V1.1, the Worker end-to-end tests share one database; run the whole suite (the two new photo tests that touch ITM-0263 run in order).
- **Branch propagation.** Every V1.2 checkpoint was merged forward through V1.15 and pushed (merge commits, no rebase). The later branches contain only specs and the shared `CLAUDE.md`, so no conflict arose.
