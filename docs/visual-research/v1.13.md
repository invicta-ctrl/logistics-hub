# V1.13 visual research and evidence: Administration and system control

Spec: `docs/specs/accepted/road-to-v2/v1.13-admin-control.md`. Product: `docs/PRODUCT_REFERENCE.md` ("Administration"). Release record: `docs/road-to-v2/releases/v1.13.md`. Screenshots are in `docs/visual-research/v1.13/`, named `admin-<section>-<scene>-<size>` with `desktop` 1440 px, `tablet` 768 px and `phone` 390 px (stored at 60–75 % of capture size, JPEG). `timings.json` is this slice.

## How the evidence was made

- The real application, production build, on a throwaway local Worker and D1 (`wrangler dev --local`), every migration applied (`0001`–`0030`), the demo catalog the migrations seed (394 active items, 141 Unclassified).
- `npm run evidence -- --out <dir> --pages admin-control`. The `admin-control` scene (`scripts/admin-evidence.mjs`) signs in as the owner and captures all five sections at three sizes: System (healthy, read from the real Worker), Self-Service with its confirmation, Catalog (classification, other names with a search, an edit sheet and a no-match state, the built-in hints, the AI panel), Staff (accounts, role guide, a role change with its impact note and its confirmation), and Accountability for an owner and for an administrator.
- The degraded, unknown-build and failed System states are the same page with the answer changed in the browser for that picture only (a pending migration, one failing bucket, Self-Service closed; no build record; a 500), because the demo database cannot be broken on purpose. The server-side behaviour behind each of them is covered by `tests/admin-control.test.ts` against real handlers.
- Every image listed below was opened and looked at. Defects found by looking, all fixed and re-rendered:
  1. **A healthy System page was drawn pink.** The healthy summary and the "no backup evidence" note reused the review callout, which is brand-tinted (oxblood in this theme), so "Everything is working" read as an alarm. They are now a neutral card with a green edge for healthy, an amber tint for attention, and a plain grey note.
  2. **"Check again" touched the status list** with no spacing; it now has a one-step gap.
  3. **"This version" rendered as three columns** because the shared `.facts` rule is a three-column grid for another page. It has its own one-column label/value list.
  4. **On a phone the static tables (backups, what phones ask for, what each role can do, built-in hints) broke**: the shared mobile table rules turn rows into grids and the sticky header row sat over the text. They are plain label/value lists now, which also read better to a screen reader than a table with no sortable data.
  5. **On a phone the summary put its heading and its list side by side**; the contents are one block that stacks.
  6. **The built-in hints list was 28 rows of three lines**, longer than everything else on the Catalog page put together. The kind (Packaging/Product) sits on the same line as the words, and the list opens from "Show all 28 hints".
  7. **On a phone the current section link was cut off** ("Ac" for Accountability) because the links scroll sideways. The current link is scrolled into view when the page draws.
- Calm, checked by eye: one accent; state is always said in words next to its dot; no row has an alarm background; the only warm tint is on a real problem; confirmation sheets put Cancel first in focus and the consequential action in the button's own words ("Close for maintenance", "Change role"), red only where the action cannot be taken back or cuts people off.
- Measured by the scene on a throwaway Worker (read the shape, not the absolute figure): the System report, which runs every check, answers in a median of 15 ms (seven runs); the System page draws its first status row in a median of 115 ms (five runs). Each check is cut at two seconds, so the worst case is bounded, and a hung storage bucket is covered by a test. Navigation did not slow: a cold load to the first Items row took 285 ms and an Items → Stock switch 69 ms in the same run.
- Not done: real phones, a screen reader, a Windows run, a dark theme (the staff workspace has none), and a review by anyone but the author.

## Sources (accessed 2026-10-07)

Read through search-result summaries in this session; I did not open the full pages.

| Source | What I took from it |
|---|---|
| [Primer: ConfirmationDialog](https://primer.style/components/confirmation-dialog) | A confirmation says what will happen in its own words, labels its buttons with the action instead of "OK", and is only for a decision that needs one. Every consequential change (Self-Service closing, role change, sign out everywhere, disable, removing old personal details) has a sheet whose confirm button names the action. Saving other names, a harmless change, has no confirmation. |
| [Cloudflare Status](https://www.cloudflarestatus.com) | One headline state first, then each component with its own state and a plain reason, and a note of when it was checked. The System page leads with "Everything checked is working" or what needs attention, then lists Application, Database, three buckets and Self-Service, each in words with its time, plus "Checked …". |
| [Google Workspace Admin help: administrator roles](https://support.google.com/a/answer/2405986) | Roles are explained as what each can do, in a list people can read before assigning one, and the most privileged role is called out. The Staff section has "What each role can do", and changing a role shows who gains or loses what before it is saved. Not copied: custom roles and privilege matrices; Logistics Hub has three roles and the spec forbids new ones. |

## What this means for Logistics Hub

An administrator opens this area to answer "is it working, which version, and what am I about to change". The page therefore says the answer in the first line, lists the evidence, never shows what it did not just check (so no backup figure, no AI usage that does not exist), and asks for a decision only where something cannot be undone or cuts people off, in the words of what will happen.
