# V1.2 visual research and evidence: item profiles and photos

Spec: `docs/specs/accepted/road-to-v2/v1.2-item-profiles-media.md`. Screenshots are in `docs/visual-research/v1.2/` (`before/` is `main` at V1.1, `after/` is this branch). They show the fictional demo accounts (Alex Reyes as Owner) and the public seed catalogue. The product pictures are boxes, bottles and rolls drawn by the evidence script on a canvas; no photograph and no image file was added to the repository for them.

## How the evidence was made

- The real application on a throwaway local Worker, D1 and R2 (`wrangler dev --local`) with every migration applied (`0001`–`0020`) and the 397 seeded items. Nothing touched the preview database or production.
- `npm run evidence -- --out docs/visual-research/v1.2 --base origin/main --pages items,item-profile,item-photos`. `items` and `item-profile` (the open profile of Scissors) render on both refs, so before and after compare. `item-photos` runs only where the photo panel exists: it draws eight pictures in the browser (landscape and portrait), adds them through the real endpoint, and captures the list, a profile with a photo, the viewer, the upload preview and a profile with no photo at desktop (1440×900), tablet (768×1024, 2×) and phone (390×844, 2×). It then measures the list with 0 and with 300 photos. Reduced motion is on for stable frames; the motion itself is tested separately (see Verification in the release record).
- Every image below was opened and looked at, not only asserted on. The first pass found real defects, listed under "What the screenshots showed". The files are WebP (quality 72); menu and staff-phone captures that did not change were dropped to keep the set at 1.5 MB.

## Patterns adopted, and why they fit Logistics Hub

- **A small fixed leading thumbnail in every row (Material lists, Polaris, Sortly, Snipe-IT).** 40 px square, centre-cropped, at the start of the item cell, so the eye finds the picture before the name. It is the 320 px variant, never the large one. Rows without a photo show a quiet outlined box, drawn as one background on the row's cell (no element, no image), so a catalogue that is mostly unphotographed still reads as a list, not as a wall of holes.
- **Fixed boxes and explicit dimensions (web.dev CLS).** The row thumbnail, the profile tile and the viewer image all have their size fixed before any byte arrives. Measured: the list's layout shift is identical with 0 and with 300 photos (0.0388 both; that figure is the list's own, already there in V1.1), so photos add none.
- **Native lazy loading (web.dev).** `loading="lazy" decoding="async"`. With 300 photos, 20 thumbnails (58 KB) load for the first screen, not 300. Rows are not virtualised: the list already renders 397 rows in one pass and the browser does the deferring.
- **A profile built around recognition (Polaris/Sortly item pages).** The photo sits beside what staff need first: availability in the large serif figure, status tags, type and category, and place. The actions for the photo (Add, Change, Remove) sit in the same column, not under the picture, because a 144 px tile has no room for them and the column beside it was empty.
- **Preview before saving (Sortly's flow, and the destructive-change rule).** Choosing a file shows what will be stored; nothing is saved until "Save photo". Remove asks first. Cancelling the file picker changes nothing.
- **Empty alt beside text, a name where the picture is the control (WAI, Polaris).** Row thumbnails are `alt=""` (the name is right there). The profile photo is a button named "View photo of {item}". The viewer's image is "Photo of {item}".
- **Native `<dialog>` for the viewer, with a view transition (APG, Chrome/MDN).** Escape, a focus trap, an inert page and focus returning to the opener come from the platform. The thumbnail grows into the viewer and back with `startViewTransition` (320 ms, the existing easing). Where the API is missing, a 200 ms fade; under `prefers-reduced-motion`, an instant open with no transition at all (tested: zero `startViewTransition` calls).
- **Back closes the viewer (phones).** The viewer holds one history entry; Back pops it, and Escape or a tap takes it back. The router now treats the address a view mirrors into the URL as "already rendered", so that entry no longer re-renders the Items page under the open item.
- **Two stored sizes, made in the browser.** 1280 px for the viewer, 320 px for lists and the profile. Re-drawing on a canvas applies the rotation and drops EXIF and GPS; the original never leaves the phone. The Worker then rebuilds each JPEG anyway, so a client that skipped the step cannot store metadata.

## Patterns rejected

- **A gallery or card view as the default for Items.** Real catalogues offer one, but the spec asks to keep efficient desktop scanning of 500+ items, and most items have no photo yet. A grid of empty cards would be slower to scan and heavier. The row thumbnail gives recognition without changing the working view.
- **Server-side resizing (Cloudflare Images binding).** It would add a binding, a billing line and an owner step for work the browser already does well before upload; it would also mean the Worker handles full-resolution originals. Rejected for this slice; revisit if staff ever upload from devices that cannot run a canvas.
- **WebP or AVIF variants.** Smaller, but Safari's canvas cannot encode WebP (it returns PNG), so the Worker would have to handle several formats. JPEG at these sizes is under 100 KB for the large variant of the test photograph.
- **A tab stop on every row's thumbnail.** 500 extra tab stops for a pointer shortcut. The same photo opens from the profile, by keyboard.
- **Keeping the original, or the EXIF "for later".** Not needed by any slice, and a location leak waiting to happen.
- **Cropping the profile photo to a square.** The tile letterboxes the photo in the preview and the viewer shows it whole; only the 40 px list thumbnail is centre-cropped, as in Sortly.
- **A JS image-viewer or animation library.** The platform does the dialog, the transition and the lazy loading. No dependency was added.

## What the screenshots showed, and what changed

First pass (rendered, then inspected):

1. **Viewer overflowed the screen on desktop.** The large image ran off the bottom and hid its caption (`max-height: 100%` had no definite height to resolve against). *Fixed:* the viewer is a block with a full-height figure; re-captured, the whole image and the caption fit at all three sizes.
2. **Photo actions were awkward.** Under the 144 px tile "Change" and "Remove" wrapped onto two lines, upload mode stacked three buttons and pushed the tabs down about 120 px on desktop, and the column beside the photo was empty. *Fixed:* actions moved into the column beside the photo; the tabs now sit about 70 px higher on a phone and about 120 px higher in upload mode on desktop.
3. **The category appeared twice** (sheet kicker and profile line). *Fixed:* the kicker is the ID only.
4. **My list capture showed no photo rows** (the search `sc` also matches the category "School Supplies"). *Fixed in the evidence script:* the first screen of the list is seeded, every third row left bare, to show the mix.
5. **Tablet: names wrapped to three lines with the thumbnail** (the baseline already wrapped long names at this width, the thumbnail made it worse). *Fixed:* the item column takes 44% at tablet widths and its ID/type line stays on one row; re-captured, names fit on one line.

Found by tests while driving the real app (not by looking):

6. **Cancelling the file picker closed the whole item sheet.** A file input fires a bubbling `cancel` event, which the shared sheet took for Escape. This also affected the loan form's photo picker. *Fixed in the shared sheet* (it reacts only to a cancel on the dialog itself); the Worker end-to-end test opens the real picker and walks away from it.
7. **After a photo change the History tab was stale** until the sheet was reopened. *Fixed.*
8. **At 320 px the sheet scrolled sideways**, because of the hidden file input positioned past the edge. *Fixed* (anchored inside the profile); asserted at 320 px.

Final captures (all reviewed): the list at 1440, 768 and 390 px shows photo and bare rows side by side with names, IDs, quantities and tags undisturbed; the profile at all three sizes shows the photo, availability, tags, type, category and place above the tabs; the viewer at all three sizes shows the whole photo and its name; the upload preview shows what will be saved with Save, Choose another and Cancel; the missing-photo state shows a dashed "Add photo" tile and a one-line hint.

## Performance (local Worker and D1, headless Chromium; medians)

**The cold-load cost, found and removed.** The first version of the list measured about 25 ms slower than V1.1 on a cold load. That figure was noisy, so I measured again with 25 interleaved runs of each tree (`.wrangler/bench.mjs`, a scratch tool, not committed) and Chrome's own counters. API time, asset loading and script time were identical; the difference was layout (+7 ms) and style recalculation (+6 ms), and the page had 1,198 more DOM nodes (13,282 → 14,480), exactly three wrapper elements for each of 397 rows. A placeholder drawn with a CSS mask looked like the culprit but was only worth about 2 ms. The fix: a row has no wrapper elements. An item without a photo adds nothing (its placeholder is a background on the cell), and an item with one adds only the image. Re-measured the same way:

| 25 interleaved runs, medians | V1.1 (`main`) | V1.2 before the fix | V1.2 after the fix |
|---|---|---|---|
| First item row | 179 ms | 189 ms | 181 ms (V1.1 in the same run: 184 ms) |
| Layout / style recalculation | 84 / 30 ms | 91 / 36 ms | 86 / 33 ms (V1.1: 87 / 29 ms) |
| Total main-thread task time | 291 ms | 314 ms | 300 ms (V1.1: 299 ms) |
| DOM nodes | 13,282 | 14,480 | 13,291 |

The remaining difference is inside the run-to-run noise (a few milliseconds). Other measurements:

A list of 300 photographed items sends about 58 KB to paint the first screen. No dependency was added.

## Not verified here

- Real phone cameras, HEIC photos, iOS Safari (its `<dialog>`, view transitions and `capture` behaviour) and screen readers. The decode path was exercised with a JPEG carrying an EXIF "rotate 90°" and GPS text; real phones differ.
- Performance on production D1 and R2 and on a real phone's network.
