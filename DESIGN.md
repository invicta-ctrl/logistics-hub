## Foundations
Preserve original licensed brand assets. Use semantic color, font, space, type, radius, elevation, focus and motion tokens. Use existing approved typography and palette; map product themes to common semantic tokens. No hardcoded ad hoc colors in reusable components. Use typography hierarchy, intentional whitespace, content-first layouts and restrained motion. Honor reduced motion.
## Distinctive design and craftsmanship
For material UI, consult relevant sections of [RESEARCH](docs/references/RESEARCH.md) §§2–4 and 7; Hallmark and Impeccable must guide the review. Establish product-specific hierarchy, typography, spatial rhythm, consistent icons and tokens before styling. Avoid automatic patterns: gratuitous arrows, pills/eyebrows, dots/numbering, one italic headline word, generic type or cream/gradient palettes, sparkle/AI icons, repetitive cards/bento, glows, decorative borders, false live dots, scroll fades, generic imagery and vague repetitive marketing copy. These are review heuristics, not bans or AI-authorship tests; use when justified. Reject fabricated statistics, testimonials, logos, status and misleading product claims.
Marketing may use monumental typography, Swiss-grid asymmetry, overlapping real product media, realistic studio lighting/shadows and one signature hero moment. Operational UI prioritizes task efficiency, predictable density, navigation and meaningful grouping. Glass, textures, effects and transitions are optional with readable/reduced-motion fallbacks. Choose coherent treatments, not a checklist of effects.
Use purposeful spacing (4px base/8px rhythm is a starting convention, not a mandate), optical alignment, comfortable line lengths, tabular numbers where useful and concentric circular radii (outer = inner + uniform inset, adjust for actual geometry). Respect safe areas, zoom/reflow and touch interaction; prefer 44 CSS px touch targets where feasible, meet applicable WCAG 2.2 AA target-size criteria (24 CSS px or permitted exception). Check relevant contrast, native semantics and representative assistive technology. No fixed palette, font or spacing treatment imposed across products.
## Design-system workflow
Use Atlassian Design System as the primary consistency reference (see ENGINEERING-BASELINE.md). Use it alongside approved visual references for product expression; do not imitate Jira branding or automatically install Atlaskit. Figma is mandatory for new shared components, design-system changes and substantial new interfaces. Record the actual file/node link and approved version or identifiable baseline, component states and responsive intent. Use an existing approved design when sufficient; if Figma is unavailable, stop affected design work and request an explicit exception before using an alternate baseline. Routine fixes do not require new mockups. Kawing-owned versioned components are canonical for implementation; use existing approved implementations until shared library adoption is accepted. Keep Figma variables/variants mapped to code tokens and component props, not a competing design system. Storybook is mandatory for shared components (states, variants, accessibility and usage); update it with code. No claim of automated Figma sync without verification.
## Components and patterns
Reuse existing components first; prefer shadcn-compatible accessible primitives and proven layouts from approved resources. One canonical component per interaction; variants via explicit props/tokens. Keep domain flows local. Define default, hover, focus, disabled, loading, empty, validation, error/retry, success, permission-denied and offline states where relevant. Ensure real destinations/actions, accurate feedback and required persistence; never misrepresent a demo as working production functionality. Native semantics, keyboard and screen-reader support, meaningful accessible names, visible focus and correct dialogs. Aim WCAG 2.2 AA; automated checks are partial.
For new material designs and shared components, follow the design-system workflow above; document props, states, usage, visual references and exact upstream licenses. Use real fixtures or clearly labeled demo data; never invent production metrics.
## Verification
Follow AGENTS visual workflow and mandatory localhost preview; inspect the actual running application or Storybook, not only screenshots or static mockups. Record baseline version; inspect desktop 1440, tablet 768 and mobile 390 or accepted widths. Test keyboard, contrast, reduced motion, overflow, touch interactions, meaningful error recovery and navigation. Run Playwright screenshot comparisons against reviewed baselines; no auto-updating expected screenshots in CI. Obtain human visual review for material changes. No unnecessary new design docs, decorative bloat, duplicative tokens or redundant component variants. Motion, graphics and dependencies must serve a measurable or clearly defined user need. Review factual copy and all applicable interaction states against the accepted project criteria, not just snapshots.
